# Reference Numbers & Identifier System
### Textile Sourcing, Traceability & Buyer CRM Platform
Feature update to Module 2 (Buyers) and Module 3 (Sister Profiles) in the Module Documentation Pack, plus a system-wide identifier rule referenced from Module 4 (Sourcing Intake) and the Packing List module. Feed this alongside Module_Documentation_Pack.md when implementing.

---

## 1. What Changed

Two auto-generated, manually-overridable reference codes were added — one for Buyer Profile, one for Sister Profile — plus a single authoritative rule clarifying which identifier is which across the whole system, since several similarly-named codes now exist (Buyer Reference, Sister Profile Reference, PO Reference, Style No, Pattern No).

---

## 2. Buyer Reference Code

| Field | Detail |
|---|---|
| Format | `BUY-0001`, `BUY-0002`, ... — continuous sequence, zero-padded to 4 digits, extends automatically past 9999 |
| Set on | Buyer Profile, at creation |
| Generation | Auto-generated by default |
| Manual override | Admin may type any value instead at creation time; system enforces uniqueness only, not the `BUY-####` format, on manual entries |
| Generation method | DB sequence (`nextval`), never a "read max, add 1" pattern — must be collision-free under concurrent creation |
| Collision handling | Manual entry that duplicates an existing code is rejected with a clear error — never silently modified or suffixed |

## 3. Sister Profile Reference Code

Same rules as above, format `SIS-0001`, `SIS-0002`, ... Set on Sister Profile at creation.

**Important:** this is a separate field from `PO Reference` (which already exists on Sister Profile). PO Reference is the buyer's own real-world PO number — always manually entered, never auto-generated, since it comes from the buyer's system, not yours. Do not merge these two fields or let one auto-fill the other.

---

## 4. Identifier Glossary (the authoritative reference — use these exact terms everywhere)

| Identifier | Set On | Format | Who/When Set | Scope |
|---|---|---|---|---|
| Buyer Reference Code | Buyer Profile | `BUY-0001` | Auto-generated at Buyer creation; manually overridable | One per buyer, forever |
| Sister Profile Reference Code | Sister Profile | `SIS-0001` | Auto-generated at Sister Profile creation; manually overridable | One per PO/order, forever |
| PO Reference | Sister Profile | Free text, e.g. `002F25BV` | Always manual — the buyer's own document number | Belongs to the buyer, not the system |
| **Style No** | Product | Free text, e.g. `MRF25` (existing garment-industry format, unchanged) | **Generated once, at Sourcing Intake.** Identifies one product/design — one Style No can have many colors under it | Read-only everywhere else it appears (Packing List, Invoice, QR) — same value, never re-entered or regenerated downstream |
| **Pattern No** | Color Row (under a Style) | Free text, e.g. `MR12528` | Entered per color row, also at Sourcing Intake | One per color; several Pattern Nos belong to one Style No |

**The rule that matters most:** Style No is the product-level identifier ("which design"); Pattern No is the color-level identifier underneath it ("which color of that design"). A Packing List line, an Invoice line, and a QR code all reference the *same* Style No + Pattern No pair generated at intake — every downstream screen displays it, none of them create a new one.

---

## 5. Implementation Rule — Reference, Don't Copy

To guarantee Style No (and Pattern No) can never diverge between Sourcing Intake and Packing List:

- **Do not** give Packing List its own independently-editable `style_no` text field that gets copied from the Product at creation time and then drifts.
- **Do** store Packing List lines with a foreign key back to the Product (`product_id`), and resolve Style No/Pattern No from that relationship at read/display/export time — or, if a denormalized copy is kept for query performance, make that copy strictly read-only and re-synced automatically whenever the source Product record changes, never independently editable.
- If two different Style No values are ever seen for what should be the same product across two screens, treat it as a data bug to fix, not as two legitimate separate identifiers.

## 6. Data Model Additions

```
BuyerProfile
  ...existing fields...
  reference_code   -- "BUY-0001", unique, auto-generated via DB sequence, manually overridable

SisterProfile
  ...existing fields...
  reference_code   -- "SIS-0001", unique, auto-generated via DB sequence, manually overridable
  po_reference     -- existing field, unchanged, always manual
```

No changes to the Product model's `style_no` / color row `pattern_no` fields themselves — this update is about the *rule* governing how they propagate, not a schema change to those two fields.

---

## 7. Acceptance Checklist

- [ ] Buyer Reference Code auto-generates as `BUY-0001`, `BUY-0002`, ... and remains unique under concurrent/parallel creation requests.
- [ ] Sister Profile Reference Code auto-generates as `SIS-0001`, `SIS-0002`, ... with the same concurrency guarantee.
- [ ] Manually entering a duplicate reference code on either entity is rejected with a clear error, not silently modified.
- [ ] PO Reference remains a fully separate, always-manual field — never auto-filled, never confused with Sister Profile Reference Code in any UI label, list column, or export.
- [ ] Style No and Pattern No, once generated at Sourcing Intake, display identically on the Packing List, Invoice, and QR code for that product — verified with a test that edits the Product after a Packing List already references it, confirming the Packing List's displayed value updates (if using live reference) or is explicitly locked (if using a synced copy) rather than silently going stale.
